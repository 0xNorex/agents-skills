# 工作成果量化

把散在各处的产出归一成一张事件表，再从这张表算所有指标。**口径先定死，数会变、口径不变。**

## 铁律（先看这四条，违反就白做）

1. **只报可追溯的数**。能落到「哪个需求 / 哪个任务 / 哪个人」的进主表；缺身份的单独列一段说明，不当成绩。
2. **不同口径的数字不能相加**。同一份产出被两种方式数过（台账去重 vs 目录文件数），相加就是虚报。
3. **代码行数不是成果**。它只做技术含量的佐证，不进数字墙。
4. **拿不到独立核对的标「未验」**。宁少数一个，不多报一个。

## 一条命令

```bash
python3 /home/zd/输出/成果量化/量化.py            # 全量：刷流水 + 出汇总
python3 /home/zd/输出/成果量化/量化.py --month 2026-10
python3 /home/zd/输出/成果量化/量化.py --src chat,covers   # 只跑部分源
python3 /home/zd/输出/成果量化/量化.py --no-net           # 不连服务器，用本地快照
python3 /home/zd/输出/成果量化/量化.py --json             # 机器可读
```

产物在 `out/`：`成果流水.csv`（统一事件表）+ `最新汇总.md` / `月报_YYYY-MM.md`。
写报告时**从这份 md 抄数字**，不要凭记忆。

## 四个数据源

| 源 | 位置 | 回答什么 | 有效期 |
|---|---|---|---|
| `scripts` | `/home/zd/narro` → `narro.stats.report()` + `narro.local_stats.merged()` | 脚本交付多少篇、分工作流/品牌 | 总量，**无月序列** |
| `jobs` | `/home/zd/narro/.narro/jobs/*` 目录名 `P<YYYYMMDD><seq>` | 每月跑了多少生产批次 | 2026-08 起 |
| `covers` | `ssh rn` → `/opt/cover-web/data/app.db` | 封面生成次数、成功率、活跃人数 | 2026-07 起 |
| `chat` | `/home/zd/输出/成果量化/data/{messages,files}.json` | 需求事件、交付动作、响应时长、需求方 | 全员周期 |

脚本产量另有权威口径脚本：`python3 /home/zd/输出/脚本统计.py --detail`（三段互不重叠，可直接相加）。

## 四类指标定义（固定，不再重新发明）

| 指标 | 定义 | 来源 |
|---|---|---|
| **需求量** | 对方消息命中请求词（辛苦/麻烦/帮我/能不能…）记为 1 个需求事件 | chat |
| **交付量** | 我方发文件 / 发文档链接 / 说「已完成」记为 1 次交付 | chat + files |
| **产出量** | 脚本按任务去重计篇；封面按成功生成计次；表格按文件数 | scripts / covers / chat |
| **响应时长** | 同一会话内「需求时间 → 其后首次交付」的小时数，只算 7 天内 | chat |

## 报表怎么写（照这个骨架，别自由发挥）

```
一、数字墙          12–15 行，每行一个数 + 一句口径
二、解决的问题      每类：痛点 → 做法 → 数字表 → 需求方原话证据
三、需求响应大盘    按需求方列交付次数，按品牌列覆盖范围
四、效率对照        之前怎么做 vs 现在，一行一个倍数
五、时间线          按月写「这个月解决了什么」，不是「这个月写了什么」
六、口径与未验      能说清每个数怎么来的，以及哪几个没独立核对
```

效率对照必须有真实锚点（人工基准 / 竞品报价 / 客户验收原话），没有锚点的不要编倍数。

## 已知坑

- **台账 `updated_at` 全是导入时间戳**（2026-10-08），不交付日 → 不能拿它做月序列，月序列用 `jobs` 批次。
- **`production.sqlite3` 的 `task` 是哈希**，不含日期；日期只在 `.narro/jobs` 目录名的 `P<YYYYMMDD>` 里。
- **封面 `artifacts` 表 2026-09 起才有记录**，7–8 月只有 `usage_events`；月序列统一用成功次数。
- **封面本地 `data/app.db` 是陈年快照**（停在 2026-09-18），线上真数在 `rn:/opt/cover-web/data/app.db`，别拿本地当全量。
- **P 编号规约 2026-08 才启用**，之前批次没有 P 前缀，`jobs` 月序列不能回溯到 4–7 月。
- **钉钉库在 `/home/zd/.config/DingTalk/<id>_v3`，是加密的**；`data/*.json` 是已解密的快照，别指望它自动更新，要新的就去重跑解密。
- 聊天里「N 条」的提及会重复计（同一批被多人多次提），只作批次规模参考，不当产量。

## 补一个新数据源

1. 在 `量化.py` 写 `src_xxx() -> (list[dict], dict)`，事件用 `ev(date, source, kind, item, qty=..., note=...)` 产出；
2. 注册到 `SOURCES`；
3. 报告表格里加一列，或在「关键结论」里加一行。

**永远先写清这个源「能回答什么、不能回答什么」**，再写代码——这是这份流程里最容易翻车的地方。
